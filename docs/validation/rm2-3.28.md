# reMarkable 2 firmware 3.28 compatibility validation

> Historical September 13 report. See the [September 15 installed-build status](2026-09-15-status.md) for current results, model default, and remaining limits. Statements below describe the earlier builds only.

2026-09-13: **expanded PDF acceptance is not complete**. Device capture/input and
numerical output repairs work, but representative messy-script recognition still fails.
The circle selects a concept; surrounding context and general knowledge are allowed. No completion PR has been published.

## Scope and setup

Development tablet: reMarkable 2, firmware 3.28.0.172, portrait orientation.
The app runs locally with a root-only OpenAI environment file. No firmware update,
account pairing or account synchronization was performed.

The source is Gundlach and Merkowitz, [Measurement of Newton's Constant Using a
Torsion Balance with Angular Acceleration Feedback](https://arxiv.org/abs/gr-qc/0006043),
[PDF version 2](https://arxiv.org/pdf/gr-qc/0006043v2). The four-page PDF was imported
through the tablet's local USB interface, which was disabled again afterward.
Its SHA-256 before and after import is
`332446943966f6c3111a09c2df05673a94282ea247bf78c946f2c6e6d479e1f6`.

A native blank notes page was inserted immediately after the first source page
using the tablet UI. Reader Buddy requires a blank or existing answer page in
that position; it does not create one automatically. All four original PDF pages
remain in order. Test questions and circles are editable ink overlays.

The pen and touch fixtures are synthetic events sent through the tablet's actual
input devices. They exercise xochitl, capture, a live GPT-4o request, navigation,
and virtual-keyboard output. They are not a human finger or handwriting sample.
Representative cursive fixtures vary slant, spacing, joined letters and shorthand.

## Repairs under test

- Locate the modern RM2 BGRA framebuffer through its validated allocation header;
  refuse ambiguous matches. Keep the existing older-RM2 and Paper Pro capture paths.
- Preserve native PDF detail in three overlapping full-width strips. Left/right
  crops split the question and caused rejection in an earlier test.
- Pace pen input and position the hovering pen before contact; reach exact endpoints.
- Evaluate the hold timer without blocking on further touch events, using completed
  input frames and the primary touch slot.
- Correct RM2 plus, equals and literal caret output. Use ASCII equation notation.
- Require a readable annotation and source outline; reject missing or malformed
  model responses instead of manufacturing a generic question.
- Wire the existing `--no-trigger` option and provide `--screenshot-only FILE`
  for bounded diagnostics without credentials or input initialization.

## Reproduction

Build with `cross build --release --target armv7-unknown-linux-gnueabihf --locked
--bins --example hardware_probe`. The offline probe's `strokes FILE.json`, `tap X Y`,
`hold`, `next`, and `previous` actions act on the currently open disposable document.
Do not run them on an unrelated document. The probe saves a screenshot after each
action. The live app can be bounded with `--once`; `--no-trigger` bypasses only the
hold, and `--debug-dump` preserves the captured request screenshot locally.

## Limits

Vision recognition is probabilistic. Passing these fixtures is not a guarantee for
all handwriting, mathematical notation, or possible page layouts. The UI uses
plain ASCII notation; arbitrary Unicode and typeset equations are not covered.
Human touch, reboot, rotation, older firmware and Paper Pro hardware have not been
validated in this run. Eraser coverage remains partial. Perplexity changes and
OpenSpec adoption (REM-21) are separate deferred work.
